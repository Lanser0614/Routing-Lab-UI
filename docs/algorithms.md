## Назначение и границы

Один снимок заказов, курьеров, настроек и времени передаётся пяти алгоритмам.
Каждый алгоритм возвращает бакеты: курьер и упорядоченный список остановок.
Общая функция проверяет вместимость, зоны и SLA, рассчитывает выезд и ETA.
Различается способ выбора заказов и построения маршрутов.

Перед построением бакетов выбирается режим дорожных данных:

| Режим | Подготовка дороги | Назначение |
| --- | --- | --- |
| `full` — сравнение | Полная общая матрица | Сравнение без ограничения соседства |
| `economy` — экономный | Филиал ↔ заказы и K ближайших соседей, расширение для неназначенных | Сокращение числа запрашиваемых ячеек |

В экономном режиме все алгоритмы используют один общий набор запрошенных переходов.
Итоговые маршруты проверяются по данным не старше 10 секунд; изменение времени
вызывает повторный расчёт. Exact тоже ограничен этим набором, поэтому его результат
и Gap не являются сравнением с полной матрицей. Детали и расход API:
[документация клиента Яндекса](yandex-matrix.md#экономный-режим).

Это сравнение независимых снимков. Расчёт в 13:30 не отправляет курьера и не удаляет
его заказы из расчёта в 13:35. Один курьер получает максимум один маршрут за запуск;
повторные рейсы в рамках запуска не моделируются. Выбор бакета на карте влияет
только на отображение.

## Входные данные

### Заказ

| Поле | Использование |
| --- | --- |
| `id` | Уникальная идентичность; последнее правило разрешения равенства |
| `status` | В расчёт входят `COOKING_STARTED`, `COOKING_COMPLETED`, `WAITING` |
| `x`, `y` | Проверка принадлежности зоне и расчёт тестовой дороги |
| `created` | Время создания; разрешение равенства при одинаковом deadline |
| `ready` | ECT: прогноз или известное время готовности |
| `deadline` | Предельное время доставки |
| `sum` | Проверка суммового лимита |
| `service` | Сохраняется в сценарии, но в этой модели ETA не используется |

Для исторического теста `createdMinutes`, `readyMinutes`, `deadlineMinutes` имеют
приоритет перед строками `HH:MM` и сохраняют секунды. Для ручных сценариев время
без даты привязывается к ближайшим суткам относительно момента планирования:
разница больше 12 часов переносится на соседние сутки. По умолчанию, если момент
планирования не задан, используется 18:00.

Общий движок получает готовые ready и deadline. Правило «создание + 35 минут»
применяется при подготовке исторических заказов; ручной сценарий использует
заданный пользователем deadline.

### Курьер и зона

В обычном режиме участвуют только `FREE` курьеры с непустым списком зон.
Порядок: `freeSince` по возрастанию, затем `id`. Время `freeSince` задаёт очередь,
но не добавляется как отдельное ограничение к выезду.

Курьер может обслужить заказ, если хотя бы одна зона точки заказа входит в его
список, а зона допускает его транспорт. Текущая зона Amir Temur не ограничивает
транспорт (`modes: null`). Положение курьера не участвует в дороге: все маршруты
начинаются в филиале.

Точки вне всех зон не участвуют в построении маршрутов и возвращаются как
`OUTSIDE_ZONE`. Заказы в прочих статусах вообще не считаются eligible.

При `alwaysFreeCouriers=true` обычный пул заменяется синтетическими курьерами:
по одному на каждый eligible заказ внутри зоны, все `FREE`, `DRIVING`, с доступом
ко всем зонам и лимитами филиала. Это устраняет нехватку курьеров, но сохраняет
ограничения вместимости и SLA.

### Настройки по умолчанию

| Настройка | Значение | Смысл |
| --- | ---: | --- |
| `allowLate` | `true` | Разрешает отдельные поздние рейсы после основного алгоритма |
| `alwaysFreeCouriers` | `false` | Включает синтетический свободный пул |
| `goOutFromBranchMin` | 2 | Время от `dep` до выхода из филиала |
| `giveOrderToClientMin` | 2 | Задержка на каждой предыдущей остановке |
| `bucketMaxFullSum` | 1 000 000 | Максимальная сумма бакета |
| `bucketMaxOrders` | 8 | Максимальное число заказов в бакете |
| `returnBufferPct` | 20 | Надбавка только к отображаемой обратной дороге |
| `matrixMode` | `full` | Полная матрица или экономный поиск (`economy`) |
| `matrixProvider` | `auto` | Источник дороги: окружение сервера, `yandex` или `local` |
| `matrixNeighbors` | 5 | Начальное число соседей в экономном режиме (1–20) |

Стандартные 12 минут приготовления — константа, а не настройка интерфейса.
Поля справочника филиала `maxLimitForCouriers` и `deltaMinutesBetweenDeliveries`
не являются дополнительными ограничениями этого движка.

## Общая проверка маршрута и времени

### Дорожная матрица

При наличии `YANDEX_ROUTING_API_KEY` используется направленная матрица Яндекса
для каждого вида транспорта. Она загружается до расчёта и общая для пяти алгоритмов.
Bulk, кеш, настройки и обработка ошибок описаны в [yandex-matrix.md](yandex-matrix.md).
Следующая формула применяется только в локальном режиме без Яндекса.

Для любой пары точек:

```text
leg(a,b) = max(0.5, round(hypot(xb-xa, yb-ya) / 20 * 2) / 2)
```

Результат в минутах, шаг 30 секунд, минимум 30 секунд. Значения кешируются по
направленной паре точек внутри запуска. Формула фактически симметрична и одинакова
для всех видов транспорта. Это геометрическая модель `LOCAL_DETERMINISTIC`:
она не учитывает дороги, пробки, одностороннее движение или реальные скорости.

### Ограничения

`evaluateRoute` последовательно проверяет:

1. Нет повторяющихся ID (`DUPLICATE`).
2. Курьер обслуживает каждый заказ (`ZONE`).
3. Число заказов не превышает `min(courier.maxOrders, bucketMaxOrders)`.
4. Сумма не превышает `min(courier.maxSum, bucketMaxFullSum)`.
5. Все заказы успевают по общей модели времени (`SLA`).

При нарушении зоны или вместимости расчёт времени для кандидата не выполняется.
Для SLA всегда проверяется весь маршрут, включая уже принятые заказы. Добавление
заказа с поздней готовностью может сдвинуть выезд и сделать ранний заказ поздним.

### Формулы IO_PLANNER_V1

Индекс остановки `i` начинается с нуля. Обозначения:

- `T[i]`: накопленная дорога филиал → остановка `i`;
- `D[i]`: deadline заказа; `R[i]`: его ready;
- `G`: выход из филиала; `H`: передача заказа клиенту;
- `P`: момент расчёта; `S`: сумма бакета; `M`: суммовой лимит филиала.

```text
handover[i] = H * i для нескольких заказов, иначе 0
LSD = min_i(D[i] - T[i] - handover[i] - G)

closingTime = min(P, LSD)       если S >= M
closingTime = max(LSD - 12, P)  иначе

dep = max(max_i(R[i]), closingTime)
ETA[i] = dep + G + T[i] + handover[i]
slack[i] = D[i] - ETA[i]

isLate = dep > LSD
status = closed, если closingTime <= P; иначе pairing
```

`LSD` — последний безопасный момент начала выезда. `dep` — начало выхода из
филиала: сами 2 минуты выхода прибавляются после него. Равенство ETA и deadline
допустимо. Передача первого заказа не прибавляется к его ETA, но задерживает
второй; это именно правило текущей перенесённой модели.

Суммовой лимит курьера проверяет вместимость, но досрочное закрытие по сумме
определяется лимитом филиала. Для допустимого маршрута условие `S >= M` обычно
означает точное достижение `M`. В этой ветке `closingTime` может оказаться раньше
`P`; дополнительного `max(dep,P)` в коде нет. Это деталь текущей реализации.

`finish` равен ETA последней остановки. Обратная дорога считается отдельно:

```text
bufferedReturnMin = leg(last, branch) * (1 + returnBufferPct / 100)
```

Она не входит в ETA, SLA или целевую функцию. Статус `closed` здесь вычислен для
снимка и сам по себе не означает реальную блокировку состава или отправку.

### Пример: заказ №55

Этот пример относится к локальной геометрической матрице. В режиме Яндекса
дорога и SLA отличаются; приведённые 6:30 не являются текущим ответом Яндекса.

Создан 13:08:05, deadline доставки 13:43:05, фактическая готовность 13:25:19.
При расчёте в 13:35, выходе 2 минуты и тестовой дороге 6:30:

```text
LSD = 13:43:05 - 2:00 - 6:30 = 13:34:35
closingTime = max(13:22:35, 13:35:00) = 13:35:00
dep = 13:35:00
ETA = 13:43:30
slack = -00:25
```

Свободный курьер не устраняет эти 25 секунд: выбранный момент расчёта уже позже LSD.

## A1: срочный seed и добавление в конец

Реализация: `appendAlgorithm(input, false)`.

1. Заказы сортируются по срочности: deadline, затем created, затем ID.
2. Курьеры рассматриваются в своей очереди.
3. Для курьера берётся первый совместимый заказ, допустимый как одиночный рейс.
   Это seed — исходный заказ бакета. Недопустимый срочный заказ пропускается.
4. Остальные совместимые заказы сортируются по дороге от последней остановки.
   При равной дороге используется срочность.
5. Выбирается первый кандидат, допустимый при добавлении в конец. Остальные
   кандидаты могут быть проверены, даже если ближайший не прошёл.
6. Процесс повторяется до отсутствия допустимого добавления; затем следующий курьер.

Порядок уже принятых остановок не изменяется. A1 старается сначала дать маршрут
срочному заказу, затем дополнить его близкими заказами. Глобальную сумму дороги
или число бакетов он не оптимизирует. Решение раннего курьера влияет на доступные
заказы для следующих.

## A2: ближайший сосед

Реализация: `appendAlgorithm(input, true)`.

Порядок курьеров и цикл добавления совпадают с A1, но срочный seed отсутствует.
Первый заказ выбирается по близости к филиалу; последующие — к последней остановке.
При равной дороге используется срочность. Каждый кандидат проверяется по всем
ограничениям, и отклонение ближайшего не прекращает поиск других кандидатов.

A2 может построить короткий локальный путь, но оставить срочный удалённый заказ
следующим курьерам. Перестановок, вставок внутрь и переноса между бакетами нет.

## A3: самая дешёвая допустимая вставка

Реализация: `insertionAlgorithm(input, false)`.

1. Создаётся пустой маршрут для каждого свободного курьера.
2. Для каждого оставшегося заказа проверяются все позиции во всех совместимых
   маршрутах: перед первой остановкой, между остановками и после последней.
3. Для каждого допустимого варианта считается:

   `delta = новая накопленная дорога маршрута - старая дорога`.

4. Из всех вариантов всех заказов выбирается минимальная delta.
5. Равенство разрешается срочностью заказа, индексом курьера, затем позицией вставки.
6. Вставка применяется; все варианты пересчитываются. Цикл заканчивается, когда
   нет ни одной допустимой вставки.

Пустой маршрут тоже кандидат: его старая дорога равна нулю. Delta не включает
выход, ожидание готовности, передачу или возвращение. SLA этих времён проверяется
отдельно. Вставка меняет порядок остановок, но принятые заказы не переносятся
между курьерами. Малое увеличение дороги сейчас не гарантирует лучший итог.

## A4: Regret-2

Реализация: `insertionAlgorithm(input, true)`.

### Что означает regret

**Regret — насколько дороже станет назначение заказа, если потерять его лучший
текущий вариант вставки и воспользоваться вторым лучшим.** Здесь «дороже» означает
дополнительные минуты дороги. Это разница двух вариантов, а не опоздание, запас
SLA или время ожидания заказа. Название можно понимать как «цена потери лучшего
варианта». Число 2 в Regret-2 означает сравнение лучших двух вариантов.

Вариант вставки — конкретный курьер и конкретная позиция в его маршруте.
Сначала варианты проходят проверку зоны, вместимости, готовности и deadline.
Затем сравнивается, сколько дороги каждый вариант добавляет к своему маршруту.

| Заказ | Лучшая вставка добавляет | Вторая лучшая добавляет | Regret |
| --- | ---: | ---: | ---: |
| A | 1 минуту | 9 минут | 8 минут |
| B | 2 минуты | 3 минуты | 1 минуту |

A4 сначала назначит **A в его лучший вариант**: у A существенно хуже запасная
альтернатива. У B два почти равноценных варианта, поэтому его можно рассмотреть
следующим. Regret 8 минут не означает, что A опоздает на 8 минут: оба сравниваемых
варианта уже прошли SLA. Для сравнения, A3 выбирает минимальную стоимость самой
вставки; например, если лучшая вставка B стоила бы 0.5 минуты, A3 выбрал бы B,
а A4 при прежнем большем regret у A выбрал бы A.

Это эвристическая оценка риска: алгоритм не утверждает, что лучший вариант
обязательно исчезнет. После каждого назначения маршруты меняются, и стоимости
вставок и regret всех оставшихся заказов рассчитываются заново.

### Расчёт и выбор

Для каждого оставшегося заказа строятся те же допустимые вставки, что в A3, и
сортируются по delta. Пусть `delta1` — лучшая, `delta2` — вторая лучшая:

```text
regret = delta2 - delta1
regret = Infinity, если допустимый вариант только один
```

Если вариант только один, потеря этого варианта оставит заказ без допустимой
вставки в текущие маршруты. Поэтому `Infinity` даёт ему приоритет перед заказами
с конечным regret; это условный приоритет, а не бесконечное время дороги.
Если два лучших варианта стоят одинаково, regret равен нулю.

Выбирается заказ с максимальным regret: потеря лучшего места для него обходится
дороже. При равном regret приоритет задаётся срочностью, затем delta лучшей вставки.
Применяется лучшая вставка выбранного заказа; альтернативы пересчитываются.

Заказ без допустимых вставок не выбирается. Второй вариант — вторая конкретная
вставка, а не обязательно другой курьер: две позиции одного маршрута считаются
разными альтернативами. В режиме одинаковых свободных курьеров одинаковые вставки
могут давать нулевой regret. Алгоритм не выполняет последующий обмен заказами.

## Exact: ограниченный перебор

Реализация: `exactAlgorithm`.

Заказы идут в порядке срочности. Для очередного заказа рекурсивно проверяются
все курьеры и позиции вставки, проходящие общую проверку; отдельная ветка оставляет
заказ неназначенным. На листе дерева сравниваются решения лексикографически:

1. Больше заказов вовремя.
2. При равенстве — меньше используемых курьеров/бакетов.
3. Затем — меньше общей дороги.
4. Затем — меньше максимальной дороги одного маршрута.

При полном равенстве сохраняется первое найденное решение. Поэтому результат
с меньшей дорогой, но большим числом бакетов не обязательно лучше для Exact.

Отсечения:

- недопустимая вставка дальше не исследуется;
- ветка отбрасывается, если даже назначение всех оставшихся заказов не позволит
  догнать лучшее число заказов вовремя;
- у одинаковых синтетических курьеров проверяется только первый пустой маршрут:
  остальные пустые маршруты эквивалентны.

Ограничения:

| Условие | Предел |
| --- | ---: |
| Заказы внутри зоны | 8 |
| Свободные курьеры в обычном режиме | 3 |
| Синтетические курьеры | Отдельный предел 3 отключён |
| Время поиска | 3000 мс |
| Состояния | 2 000 000 |

Время и число состояний проверяются раз в 256 входов в рекурсию: пределы могут
быть немного превышены. При превышении возвращается skipped, а не найденное
частичное решение. Late solo для skipped результата не выполняется.

Название Exact означает полный поиск в реализованном дереве допустимых вставок.
Важно учитывать границу: недопустимые промежуточные маршруты отсекаются. Общая
формула закрытия меняет ветку при достижении суммового лимита, поэтому нельзя без
отдельного доказательства считать результат эталоном для всех возможных финальных
маршрутов и любых настроек. Это также не эталон реальной дорожной оптимизации:
используется выбранная общая матрица дороги (Яндекс или локальная геометрия).

## Завершение расчёта

### Late solo

Основные алгоритмы принимают только маршруты без нарушения SLA. После этого
`finish` при `allowLate=true` рассматривает оставшиеся заказы по срочности.
Для каждого ищет первого неиспользованного совместимого курьера, у которого
одиночный маршрут нарушает только SLA. Такой заказ получает отдельный бакет
с `late=true`. Вместимость и зоны по-прежнему обязательны.

Поздние заказы не добавляются в существующие бакеты и не объединяются между собой.
Проверка в коде допускает также отсутствие нарушений; метка late в этом этапе
задаётся самим способом назначения. Метрика «вовремя» считается по метке маршрута.

### Неназначенные заказы

| Код | Как определяется |
| --- | --- |
| `OUTSIDE_ZONE` | Заказ вне всех зон |
| `UNREACHABLE` | Все проверенные вставки нарушают доступность дороги |
| `MATRIX_NOT_REQUESTED` | Среди вставок есть ещё не запрошенный переход экономной матрицы |
| `NO_COURIER` | Нет участвующих курьеров |
| `NO_ZONE_COMPATIBLE_COURIER` | Нет совместимого курьера по зоне/транспорту |
| `ALGORITHM_CHOICE` | После построения решения ещё существует допустимая вставка |
| `MAX_ORDERS` | Все проверенные вставки нарушают числовой лимит |
| `MAX_FULL_SUM` | Все вставки нарушают числовой или суммовой лимит, но не выполнено предыдущее условие |
| `SLA` | Остальной случай при наличии совместимых курьеров |

Причина выводится диагностической проверкой вставок в итоговые маршруты.
Это классификация по правилам кода, а не доказательство невозможности любого
другого распределения заказов.

Trace содержит seed, принятые вставки, отказы, regret, улучшения Exact и итог.
Возвращается максимум 10 000 записей; отсутствие записи не доказывает, что
кандидат никогда не рассматривался.

## Метрики

| Метрика | Определение |
| --- | --- |
| Вовремя | Число заказов в маршрутах без метки late |
| Late solo | Число отдельных маршрутов с меткой late |
| Не назначено | Длина списка unassigned, включая вне зоны |
| Бакеты | Все непустые маршруты, включая late |
| Общая дорога | Сумма `travel` всех маршрутов, включая late |
| Максимальный маршрут | Максимальный `travel`, включая late |
| Минимальный запас SLA | Минимум `deadline - ETA` только среди маршрутов без late; null, если их нет |
| Matrix | `(число eligible заказов внутри зоны + 1)²` |
| Расчёт | Время выполнения основной функции алгоритма в миллисекундах |
| Gap к Exact | Сначала недостаток заказов вовремя, иначе относительная разница дороги |

Общая дорога включает филиал → первый заказ и перемещения между заказами.
Она исключает обратный путь, ожидание, выход и передачу клиенту. Matrix — размер
теоретической квадратной матрицы с филиалом, а не число HTTP-запросов: внешнего
дорожного API в локальном режиме нет; в режиме Яндекса расход отражён в `matrixStats`. Время «Расчёт» не включает последующий `finish` с late
solo и итоговой диагностикой; матрица кешируется совместно между алгоритмами.

Gap при меньшем onTime показывает, например, `−2 зак.`. Иначе:

```text
gap = max(0, round((travel_algorithm - travel_exact) / travel_exact * 100))
```

Если дорога Exact нулевая, отображается 0%; если сравнение недоступно — «—».
Отрицательная разница дороги также отображается как 0%. Gap не отражает всю
лексикографическую цель Exact: в нём нет отдельного штрафа за лишние бакеты.

## Исторические тестовые заказы

Источник — `Explore-logs-2026-10-01_unique_eventInfo_id.json`.
Скрипт извлечения: [extract_test_orders.py](../scripts/extract_test_orders.py).
Данные: [orders-2026-10-01.json](../test/fixtures/orders-2026-10-01.json).

Из 328 строк выделено 84 уникальных заказа. В fixture 79: исключены 3 заказа
с финальной отменой и 2 самовывоза. У 288 строк внутренний JSON обрезан;
берутся только полностью читаемые поля. Телефоны, имена клиентов и детали адреса
не копируются. Координаты фиксированы по последней извлечённой версии.

Правила времени:

- `createdAt` берётся из IIKO `whenCreated`.
- **Deadline доставки = createdAt + 35 минут.**
- `completeBefore` сохраняется в событии как `cookingCompleteBeforeAt`: это
  кухонное время, оно не участвует в SLA доставки.
- Первоначальный ready = `cookingStartTime + 12 минут`; при отсутствии начала
  используется создание заказа.
- Фактический `whenCookingCompleted` используется только после наблюдения события,
  в котором он появился. Будущие события не доступны предыдущему снимку.
- Сумма берётся из `sum`; исходный `fullSum` до скидок отсутствует.

Выбранный час задаёт **час создания заказов**, нижняя граница включена, верхняя
исключена. Например, 13:00–14:00 не включает заказ №49, созданный в 12:57.
Внутри часа выбирается момент расчёта с шагом 5 минут. По умолчанию — момент
с максимальным числом активных заказов; при равенстве более ранний.

На момент расчёта включаются только уже наблюдавшиеся заказы с подходящим
последним статусом и ещё не истёкшим deadline. `WaitCooking` для теста сопоставлен
с `COOKING_STARTED` как явное упрощение. После наблюдения `OnWay` заказ исключается.
В тестовом режиме свободные синтетические курьеры включены принудительно.

Ограничения исторического теста:

- Истёкшие deadline исключаются, чтобы неполный экспорт не сохранял устаревшие
  Waiting бесконечно; поэтому отчёт не показывает все уже просроченные заказы дня.
- Заказы с финальной отменой исключены целиком, в том числе из срезов до отмены.
  Например, №45 отсутствует; это известное ограничение исторической реконструкции.
- Предыдущий час не переносится в выбранный час даже при наличии активных заказов.
- Между снимками не сохраняются виртуальные назначения или отправления.
- Результат не доказывает, что реальный курьер опоздал: источник дороги зависит от конфигурации, экспорт
  событий неполный, модель делает новый план в выбранный момент; Яндекс не восстанавливает исторические пробки.

Тестовый API не изменяет рабочий SQLite-сценарий. Изменённые сроки требуют нового
расчёта: сохранённые результаты старых запусков не переписываются автоматически.

## Отличия от IO Planner

В прототип перенесены формулы времени бакета. A1 — локальная реализация подхода
со срочным seed, а не полная копия жизненного цикла рабочего сервиса.

В локальном коде IO Planner `app/kafka/consumers.py` ECT сначала равен
`cooking_started_at + 12 минут`, затем заменяется `cooking_completed_at`, когда
это поле приходит в событии. Прогноза по составу заказа в проверенном пути нет.
Обновление статуса запускает новый цикл планирования.

Проверенный consumer IO Planner получает собственное поле `complete_before`
в контракте Delivery IO и добавляет продление outage. Это отдельный контракт;
нельзя автоматически отождествлять его с кухонным IIKO `completeBefore` из сырого
тестового лога. Правило создания + 35 минут в этой лаборатории не изменяет
production IO Planner.

В Routing Lab есть прямой клиент Яндекс Matrix, но отсутствуют production Geomatrix, прогноз по составу блюд,
outage detection и продление SLA, сканирование/разблокировка, резервирование
курьеров, реальная отправка, последовательные рейсы и сохранение жизненного
цикла бакетов между снимками. Поэтому обновлённый ready при новом запуске
может полностью изменить бакеты, включая ранее отображавшиеся как closed.
Из этого нельзя делать вывод о пересоздании закрытых бакетов в IO Planner:
его жизненный цикл нужно проверять отдельно.
