# Kafka: режим наблюдения

Запуск: Node.js 22.13+ с node:sqlite, `npm ci`, заполнить `.env` по `.env.example`, установить `KAFKA_OBSERVER_ENABLED=true`, затем `npm start`. Для сервера сохранять каталог `data` на постоянном диске. Разворачивать один экземпляр с этой SQLite-базой. Интерфейс доступен на PORT (по умолчанию 3000).

Два отдельных consumer читают `delivery-io.order-status` и `courier-io.status`. Контракты и SASL_SSL/SCRAM-SHA-512 взяты из `bellissimo-io-planner/app/kafka/{schemas,consumers}.py`. Значение — JSON envelope с `payload`. Фильтр: `payload.branch_id` (либо явно переданный `organizationId`) строго равен `9f5b02ea-b7c5-450c-8b1e-d66ccd72f9dd`. Это IIKO UUID филиала Amir Temur, не числовой ID 24.

Брокеры и учётные данные задаются через KAFKA_BROKERS, KAFKA_USERNAME, KAFKA_PASSWORD, KAFKA_SASL_MECHANISM, KAFKA_CA_LOCATION. Секреты не копируются из рабочего сервиса. При username включается TLS с проверкой сертификата. Для TLS без SASL использовать KAFKA_SSL=true. Группы `<KAFKA_CONSUMER_GROUP>-orders` и `...-couriers` отдельные от IO Planner; его стандартная группа запрещена. Клиент не создаёт топики, не содержит producer и не вызывает рабочие HTTP-сервисы. Нужны права чтения двух топиков и работы со своими consumer groups.

По умолчанию новая группа начинает с новых событий: уже существующие сущности появятся после очередного события. KAFKA_FROM_BEGINNING=true читает доступную историю при отсутствии committed offsets; прежние offsets сохраняют приоритет. История Kafka может быть неполной из-за retention. Перед оценкой дождаться загрузки обоих потоков. UI обновляется каждые 5 секунд, все алгоритмы пересчитываются каждые 15 секунд. `/health` возвращает 503, пока оба consumer не вступили в группы; `/api/v1/observer` показывает счётчики, последний timestamp, исключённые заказы. Подключение ещё не означает полноту состояния.

Live-база по умолчанию `data/observer.sqlite`, отдельно от тестовой. Данные и offsets записываются одной транзакцией SQLite, затем вручную подтверждается следующий offset Kafka. Повторы отсеиваются по topic/partition/offset; старые события сущности по timestamp не заменяют новые. Ошибочный JSON/контракт учитывается как invalid и пропускается; ошибки SQLite не подтверждаются. Snappy поддерживается. SIGINT/SIGTERM отключают consumer. При ошибке старта процесс завершается; runtime crash отражается в health, KafkaJS выполняет свои retries. Существующая база без признака observer отклоняется, чтобы не смешивать live-данные с тестами.

## Точность расчёта

Начало заказа — timestamp события со статусом `WaitCooking` (payload.timestamp, иначе timestamp envelope). По согласованному правилу deadline = первое время WaitCooking +35 минут. Начало сохраняется в SQLite как waitCookingAt и не сдвигается при следующих статусах или перезапуске. Поздно доставленный WaitCooking дополняет время начала, не откатывая текущий статус. Повторный WaitCooking не продлевает SLA. До CookingStarted готовность оценивается как WaitCooking +12 минут; затем используется cooking_started_at +12 либо фактический cooking_completed_at.

Если WaitCooking не прочитан (например, новая группа запущена после этого события), используются дополнительные created_at/whenCreated, когда они переданы. Без них заказ отмечается CREATED_AT_MISSING и исключается из расчёта. KAFKA_FROM_BEGINNING=true позволяет прочитать доступную историю новой группой, но не восстанавливает события, удалённые retention. complete_before не используется для deadline.

Если осознанно включить KAFKA_ALLOW_COOKING_START_DEADLINE=true, время создания заменяется cooking_started_at; deadlineBasis=cooking_started_at_approximation явно отмечает приближение. Такой результат нельзя считать точной проверкой правила «создан +35». Готовность: cooking_completed_at либо cooking_started_at +12 минут. Отсутствие времени приготовления, координат, неизвестный статус или некорректная сумма исключают заказ с диагностикой. must_be_scanned=true также исключает заказ до завершения сканирования: полноценная модель scan-locked bucket пока не реализована.

Реальные FREE курьеры участвуют в расчёте, RETURNING/RESERVED/DELIVERING/OFFLINE не назначаются. Синтетические всегда свободные курьеры отключены. CAR/SCOOTER/BICYCLE/PEDESTRIAN переводятся в режимы прототипа. Топик не содержит лимиты и зоны курьера: используются локальная Z1 и явно настраиваемые OBSERVER_COURIER_MAX_ORDERS (3), OBSERVER_COURIER_MAX_SUM (300000). Роль сохраняется, но ограничения ролей не моделируются. Конфигурация филиала, outages, реальные существующие bucket/назначения и динамические зоны из этих потоков не восстанавливаются. Это сравнение гипотетических новых бакетов на текущем состоянии, а не полная копия IO Planner.

По умолчанию дорога локальная, без запросов Яндекс. В observer API все изменения настроек/сущностей запрещены; доступен ручной запуск расчёта, он сохраняет только локальный результат. Никакие расчётные назначения не меняют исходные статусы и не отправляются в Kafka. Для SQLITE_PATH допускается только новый файл либо ранее инициализированная observer-база; существующая тестовая база отклоняется.

Механизм ручного подтверждения offsets: [KafkaJS consuming](https://kafka.js.org/docs/consuming).
